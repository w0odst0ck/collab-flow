## 0. 定位、范围与红线

### 0.1 P3 一句话

把真实设计器（dsh-design，经 flow-config 配置注入）与真实执行器（reasonix，经 rx 封装）接进 P2 状态机，新增 `design`/`execute` 子命令，把 `verify` 从「人工写 verify.json」升级为「测试全过 + diff 对照 + 错误处理表核对」的真实测试门，让 `created→…→verified` 全链路自动推进。

### 0.2 与 P2 的边界（严格遵守）

| 项 | P2 现状（保持不变） | P3 增量 |
|---|---|---|
| 状态机 | 8 态全流转 + 9 守卫 + verify_fail 双路由 | **零改动**：`transition()/evaluate_guard()/TRANSITIONS/GUARDS/VERIFY_FAIL/EVENT_REQUIRED_CTX` 一字不动 |
| 11 子命令 | new/status/transition/list/log/lock/unlock/show/guard/verify/decision | **行为不变**；仅新增 `design`/`execute` 两个子命令 + `verify --auto` 新增开关 |
| 守卫 | brief_required/taskbook_required/test_gate_pass 等已就绪 | **零改动**：ctx 数据源从「模拟文件」换成「真实生产方产物」 |
| verify.json | schema v1 已定（§1.6 P2） | 只**填真实值** + 扩展 `details`，读取方（守卫）零改动 |

### 0.3 红线（逐条锁定，交付物可审计）

1. **P1 文件零改动**：`scripts/dsh-design`、`scripts/flow-config`、`scripts/flow-config-core.py`、`scripts/dsh-design-stats.py` 一字不动；`tests/run-smoke.sh`、`tests/run-config-smoke.sh` 断言不动。
2. **P2 既有行为不变**：`flow-core.py` 只做增量（新命令 + 执行器适配层 + 一处向后兼容解析器扩展），现有 11 子命令的既有行为与 33 单测 + 现有 CLI 冒烟全绿。
3. **零新依赖**：bash + python3 stdlib-only；YAML 继续用自包含受限解析器；测试全程 stub/临时目录/零 API。
4. **执行器写权限关进测试门**：executor 沙箱 `workspace-write`；verify 用 `git diff` 强制核对改动范围。
5. **key 不注入不落盘**：reasonix 的 key 由执行节点本地 `~/.reasonix/.env` 自读；flow 适配器不读、不传、不落盘，仅对日志做 `sk-` deny-list 防御性 redact。
6. **零个人标识**：deny-list `/home/[^~]|sk-[A-Za-z0-9]{10}` 对全部新增文件零命中；`rx`/`.env` 路径一律用 `~`/PATH 解析，不写真实 home 绝对路径。
7. **真实 reasonix 调用只在手动端到端验证**，绝不进 CI。

## 2. 三个子命令完整语义

### 2.1 公共约定

- **命令面**：`flow workitem design|execute|verify …`（design/execute 为新增 workitem 子命令；verify 为既有子命令新增 `--auto`）。薄壳 `flow` 逻辑零改动，仅 usage 文案追加。
- **工作目录**：`workdir = os.getcwd()`（项目仓根，`data_dir()` 默认 `cwd/.flow`）。设计器在 `workdir` 内 read-only 运行；执行器在 `workdir` 内 workspace-write 运行；测试命令在 `workdir` 内运行。可用 `FLOW_WORKDIR` 覆盖（P4 执行面用）。
- **退出码统一**：`0` 成功 / `1` 运行失败（守卫拒绝、执行器失败、测试门未过）/ `2` 用法或前置错误 / `124` 超时（透传）。`--json` 契约：成功 stdout 单行 JSON，失败 stderr 单行 `{"status":"failed","error":…,"detail":…}`。
- **锁/事件/落盘**：design/execute/verify 复用 `cmd_transition` 的锁与落盘路径（抽取共享辅助 `_do_transition(wi_dir, from_state, to, event, overrides, meta, cfg)`，不改变现有 transition 行为）：`with_workitem_lock` 内读 status → 判逻辑锁 → `transition()` 纯判定 → `append_event`（seq 镜像）→ `save_status_atomic`。执行器子进程（reasonix）运行期间**不持有** workitem flock，只在写工件 + 转移时加锁。

### 2.2 `flow workitem design <id>`

**参数**：`flow workitem design <id> [--force] [--json]`
- `--force`：跳过「state==created」前置与守卫，允许重跑设计器并覆盖 `design.md`（仍强制走 `transition(force=True)`，但**不**跳过 dsh-design 内部的 pro 回验/read-only 红线）。

**前置**：work-item 存在且 `state == created`（否则 exit 2）；`brief.md` 非空（否则 exit 2，守卫 `brief_required` 也兜底）。

**数据流**：
1. `resolve_wi_dir(id)`，读 `brief.md`。
2. 调 `scripts/flow-config -d <workdir> -o <tmp> --json .flow/workitems/<id>/brief.md`（**复用 P1，零改动**：flow-config 渲染 defaults+user 的 `DSH_DESIGN_*` env → exec dsh-design，pro 强制 / read-only / 回验 fail-closed / key redact 全部继承）。
3. 捕获单行 JSON `{"design": <path>, "model":…, "session":…, "usage":…, "duration_s":…}`。
   - rc=124 → exit 124；rc=1/2 → 不写 design.md、不转移，透传 rc + 错误。
4. 把产物 `.md` 内容原子写为 `.flow/workitems/<id>/design.md`（temp+fsync+os.replace）。
5. 写 `.flow/workitems/<id>/design-result.json`：`{"schema_version":1,"adapter":"dsh-designer","model":…,"session":…,"usage":…,"duration_s":…,"source": <dsh 产物相对名>,"checked_at":…}`（P5 复盘输入）。
6. `_do_transition(created → designed, event=design, guard=brief_required)`，event meta 记 `{"adapter":"dsh-designer","model":…}`。

**退出码**：0 成功 / 1 dsh-design 失败（回验失败、空输出、dsh 失败）/ 2 前置或用法 / 124 超时。

**--json 成功**：
```json
{"status":"ok","id":"w1","from":"created","to":"designed","event":"design","guard":"brief_required",
 "design":".flow/workitems/w1/design.md","model":"deepseek-v4-pro","usage":{…},"duration_s":385}
```

**与守卫衔接**：`brief_required` 由 `build_ctx` 读 `brief.md` 自然生效；dsh-design 的模型回验是 fail-closed 的**前置**（回验失败根本不落 design.md，也就进不了 designed）。

### 2.3 `flow workitem execute <id>`

**参数**：`flow workitem execute <id> [--executor NAME] [--timeout N] [--force] [--json]`
- `--executor`：覆盖 `defaults.executor.default`（默认 `reasonix`）。
- `--timeout`：覆盖 spec 的 `invoke.timeout_s`。
- `--force`：跳过「state==translated」前置与守卫。

**前置**：state == translated（否则 exit 2）；`taskbook.md` 非空（守卫 `taskbook_required` 兜底）；git 可用（否则 exit 2「需要 git」）；执行器 spec 合法且 `runtime.os` 匹配当前平台、`invoke.sandbox == workspace-write`（否则 exit 2 fail-closed）。

**数据流**：
1. `load_executor_spec(name)` → spec；校验（§3.1）。
2. git 前快照：`git -C <workdir> rev-parse HEAD` + `git status --porcelain`（记录基线，供 diff 与 scope 核对）。
3. 调 wrapper：`<wrapper> --taskbook .flow/workitems/<id>/taskbook.md --workdir <workdir> --out .flow/workitems/<id>/executor --timeout N`（wrapper 契约 §3.2；reasonix 经 `rx`，sandbox workspace-write）。
4. 读 `executor/result.json`（缺失/损坏 → exit 2，不转移）。
5. 按 `result.status` 分流：
   - `ok`（exit 0）→ `_do_transition(translated → executed, event=execute, guard=taskbook_required)`，meta 记 `{"executor":"reasonix","duration_s":…}`。
   - `failed`（exit 1）→ 只落 result.json，**不转移**（state 留 translated 可重跑），exit 1。
   - `timeout`（exit 124）→ 只落 result.json，不转移，exit 124 透传。

**退出码**：0 成功（转移 executed）/ 1 执行器失败 / 2 前置/用法/result 缺失 / 124 超时。

**--json 成功**：
```json
{"status":"ok","id":"w1","from":"translated","to":"executed","event":"execute","guard":"taskbook_required",
 "executor":"reasonix","exit_code":0,"diff":{"files_changed":3,"insertions":42,"deletions":7}}
```

**与守卫衔接**：`taskbook_required` 自然生效；执行器成败不进守卫（守卫只认 taskbook 非空），**是否转移由适配器按 exit code 决定**——这是「执行器是生产方、守卫是门禁」的边界：守卫守「有没有任务书」，适配器守「执行器有没有成功」。

### 2.4 `flow workitem verify <id>`

**参数**：`flow workitem verify <id> [--auto] [--tests b] [--diff b] [--errors b] [--route design|impl] [--test-command CMD] [--scope FILE] [--no-transition] [--json]`

**两种模式（关键兼容决策）**：

| 模式 | 触发 | 行为 | 目的 |
|---|---|---|---|
| **P2 兼容**（模拟） | **无 `--auto`** | 完全沿用 P2：`--tests/--diff/--errors`（默认全 true）写 verify.json，`--route` 仅在失败时必填 | C14 等现有 CLI 冒烟依赖 `verify <id>`（裸调）产出 all-pass；**一字不改** |
| **P3 自动化** | `--auto` | 真实执行三条件 → 写 verify.json + verify.md → 自动转移（见下） | 端到端自动化测试门 |

> **为何自动化放在 `--auto` 而非裸 `verify`**：红线「不得改变现有 11 子命令既有行为」是硬约束；现有 `run-flow-smoke.sh` C14 用裸 `verify w1 --json`（临时目录、无 result.json、无测试命令）产出 all-pass 并推进到 verified。若裸 verify 改自动化，C14 必挂。故自动化以 `--auto` 显式 opt-in，裸 verify 保持 P2 语义。此即「自动化有限部分明确边界」的 CLI 层落地。

**`--auto` 数据流**：
1. `resolve_wi_dir`；前置 state == executed（否则 exit 2「先 flow workitem execute」），`executor/result.json` + `diff.patch` 存在（否则 exit 2）。
2. **tests**（§4.1）：解析测试命令 → 在 `workdir` 运行 → `tests_pass = (exit 0)`。
3. **diff**（§4.2）：读 result.json 改动文件集 → 对照 scope → `diff_match`。
4. **errors**（§4.3）：解析 design.md 附录错误处理表 → 逐条核对 → `error_table_match`。
5. 写 `executor/verify.json`（schema §4.4，含 `details`）+ `verify.md`（人读结论）。
6. 路由（`gate_pass = tests_pass && diff_match && error_table_match`）：
   - `gate_pass` → `_do_transition(executed → verified, event=verify, guard=test_gate_pass)`，exit 0。
   - `!gate_pass` → 推导 route（可用 `--route` 覆盖，见 §4.4 推导表）→ `_do_transition(executed → designed|executed, event=verify_fail, guard=test_gate_fail_design|impl)`，exit 1（「门未过，已打回」）。
   - `--no-transition`：只评估 + 落盘 verify.json/verify.md，不转移（干跑/审查用），exit 按 gate 判定。

**退出码（--auto）**：0 门通过（→ verified）/ 1 门未过（已按 route 打回）/ 2 前置或用法 / 124 测试命令自身超时（→ tests_pass=false，按 impl 路由）。

**--json**：
```json
// 通过
{"status":"ok","id":"w1","gate":{"tests_pass":true,"diff_match":true,"error_table_match":true},
 "transition":{"from":"executed","to":"verified","event":"verify","guard":"test_gate_pass"}}
// 失败（stderr, exit 1）
{"status":"failed","id":"w1","gate":{"tests_pass":true,"diff_match":false,"error_table_match":true},
 "route":"impl","transition":{"from":"executed","to":"executed","event":"verify_fail"}}
```

## 3. ExecutorSpec 契约与适配器

### 3.1 ExecutorSpec 结构（受限 YAML：映射 + list-of-mapping + 标量）

> 关键：spec.yaml 必须可被 `flow-core.py` 现有 `parse_yaml` 解析——故**禁用流式集合/锚点**，`os/args` 用受限形式表达（见下）。这比架构 §2.2 的 `{…}` 内联式更贴合 P2 解析器，且零新依赖。

```yaml
# executors/reasonix/spec.yaml
id: reasonix
version: "1.0.0"
runtime:
  os: linux               # 能力声明；reasonix Linux-only（P4 执行面 preflight 校验用）
  shell: bash
capabilities:
  execute: true
  plan: false
  cost_report: true       # 是否产出自报成本；reasonix 现状不产（cost 留 null）
invoke:
  binary: rx              # PATH 解析（~/.local/bin/rx）；config 可覆盖
  args_template: run -y "TASKBOOK_CONTENT"   # 模板占位：TASKBOOK_CONTENT 由 wrapper 注入
  timeout_s: 1800
  sandbox: workspace-write
input:
  taskbook: file
  workdir: dir
output:
  result_manifest: result.json
  diff: diff.patch
  cost: cost.json
exit_codes:
  ok: 0
  failed: 1
  timeout: 124
```

**字段语义与校验**（`load_executor_spec()` 加载 + 校验，非法 → exit 2 fail-closed）：
- `id`：`[A-Za-z0-9][A-Za-z0-9._-]{0,63}`。
- `runtime.os`：单标量（P3 只支持单平台声明；多平台用 `os.linux/darwin/windows: true|false` 映射表达，解析器已支持，P4 再扩）。当前平台不匹配 → exit 2（能力声明前置校验，显式化 reasonix Linux-only）。
- `invoke.sandbox`：执行器**必须** `workspace-write`；`read-only` 对 executor 非法 → exit 2（架构 §2.2 红线）。
- `invoke.timeout_s`：正整数；`--timeout` 覆盖。
- `exit_codes`：固定三态映射（0/1/124），wrapper 透传约定。

### 3.2 wrapper 契约（执行器适配器 = spec.yaml + wrapper.sh）

通用调用面（`flow-core.py` 的 `run_executor()` 与任意执行器 wrapper 之间的唯一契约）：

```
<wrapper> --taskbook <path> --workdir <dir> --out <dir> [--timeout N]
```

**wrapper 职责（必做，否则契约测试失败）**：
1. 读 taskbook 内容；`cd <workdir>`。
2. 运行底层二进制（经 `timeout N` 包裹），捕获 stdout/stderr 与退出码。
3. **redact**：对捕获日志过 `sk-[A-Za-z0-9]{10}` deny-list，命中即替换为 `[REDACTED]`（无 python3 时整段占位 `[REDACTED]`，绝不回退原文）——key 本身不读不传。
4. 产出 `git diff`（HEAD vs 工作树，含 `--stat` 与 `--name-only`）→ `<out>/diff.patch`；untracked 用 `git status --porcelain` 单独列出。
5. 写 `<out>/result.json`（§3.4），`status` 映射退出码：0→ok、1→failed、124→timeout。
6. 退出码透传：0/1/124。

**新增执行器 X**（P4/P6 复用）：`executors/x/spec.yaml` + `executors/x/wrapper.sh`（~50 行，复用本契约），必须先过 stub 契约测试（§5）。

### 3.3 reasonix-executor 适配器（默认执行器）

`executors/reasonix/wrapper.sh` 核心逻辑（~50 行，复用 dsh-design 的 `cd realpath / timeout / exit 透传 / redact` 模式）：

```bash
set -uo pipefail   # 不 set -e；不 set -x（防 key）
# 1) 参数解析 --taskbook/--workdir/--out/--timeout（getopt）
# 2) WORKDIR="$(readlink -f "$workdir")"; OUT="$(readlink -f "$out")"; mkdir -p "$OUT"
# 3) TASKBOOK="$(cat "$taskbook")"          # 任务书即 reasonix 的「任务书」文本
# 4) cd "$WORKDIR"
# 5) before=$(date +%s); timeout "$T" rx run -y "$TASKBOOK" >"$OUT/.run.out" 2>"$OUT/.run.err"; rc=$?
#    DUR=$(( $(date +%s) - before ))
# 6) redact "$OUT/.run.out/.err" 中的 sk-* → [REDACTED]（不读 key）
# 7) git diff HEAD >"$OUT/diff.patch"; git diff --stat/--name-only; git status --porcelain
# 8) 按 rc 组装 result.json（status=ok|failed|timeout）写入 "$OUT/result.json"
# 9) exit $rc（透传 0/1/124）
```

**invoke 映射**（spec → 实际调用）：
- `binary: rx` → PATH 解析 `rx`（`~/.local/bin/rx`）；`args_template: run -y "TASKBOOK_CONTENT"` 中的 `TASKBOOK_CONTENT` 由 wrapper 用任务书文本替换（reasonix `run -y` 接受任务书字符串）。
- 日志落盘：reasonix 自身写 `~/.reasonix/runs/`（其内部行为，flow 不介入不读取）；flow 只在 `executor/` 落 result.json/diff.patch/redacted 日志尾部。
- **超时透传**：`timeout` 返回 124 → wrapper exit 124 → result.status=timeout → execute exit 124。
- **redact**：不读 key（红线），仅 deny-list 扫 `sk-`（防御 reasonix 日志误带）。

### 3.4 `executor/result.json` schema

```json
{"schema_version":1,"executor":"reasonix","status":"ok","exit_code":0,
 "duration_s":123,
 "diff":{"files_changed":3,"insertions":42,"deletions":7,
         "changed_files":["scripts/flow-core.py","tests/test-executor.py","executors/reasonix/wrapper.sh"],
         "untracked_files":[],
         "patch":"executor/diff.patch"},
 "test_command":null,
 "cost":null,
 "redacted_logs":"…(过滤后日志尾部, 无 key)…",
 "started_at":"2026-08-14T10:00:00+00:00","finished_at":"2026-08-14T10:02:03+00:00"}
```

- `status ∈ {ok,failed,timeout}`；`diff.patch` 为 git 统一补丁（对照方案的唯一权威）；`test_command` 为执行器自报测试命令（reasonix 现状填 null，识别回退到 §4.1 其它层）。
- `redacted_logs`/任何落盘字段写前过 deny-list（`sk-…` 拒绝/替换），复用 `append_event` 的 `DENY_RE` 模式。

## 4. verify 测试门自动化

### 4.1 测试命令识别机制（选型 + 理由）

**候选**：① taskbook 验收标准约定字段 ② result.json 记录 ③ 项目测试惯例探测。

**选型：分层解析 + 显式优先 + fail-closed**（不单选，按确定性降级）：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `verify --test-command CMD` | CLI 显式（人工/CI 覆盖） |
| 2 | `executor/result.json.test_command` | 执行器自报（执行器最懂项目） |
| 3 | taskbook.md ` ```flow ` 前置块 `test_command` | **结构化**声明（critic 翻译时填，机器可读） |
| 4 | 项目惯例探测 | `Makefile(test/check)` → `package.json(scripts.test)` → `pytest`(pytest.ini/pyproject) → `unittest discover tests` |
| 5 | 无 | **fail-closed**：`tests_pass=false`，reason=`test_command_unresolved` |

**理由**：
1. 任务书**自由文本**（【验收标准】章节）解析脆弱（编号/命令/多行变体），不适合做唯一真源 → 故在任务书模板加**结构化 ```flow 前置块**承载 `test_command`（零解析歧义），自由文本只作人读。
2. 执行器自报（result.json）优先级高于任务书声明，因执行器运行于项目内、对实际测试方式最知情；但 reasonix 现状不可靠自报 → 允许 null 回退。
3. 惯例探测是**最后便利手段**，可能误判（同名 Makefile target 非测试），故探测结果不确定时**必须 fail-closed 而非静默通过**——宁可打回 critic 补声明，不冒「假绿」风险。
4. `--test-command` 是人工/CI 显式覆盖，满足「自动化有限部分可人工兜底」。

**任务书前置块**（`templates/任务书.md` 新增说明，可选，缺失不报错但触发回退）：
````markdown
```flow
test_command: python3 -m unittest discover tests && bash tests/run-executor-smoke.sh
diff_scope:
  allow:
    - scripts/flow-core.py
    - tests/test-executor.py
    - executors/reasonix/wrapper.sh
  deny:
    - scripts/dsh-design
    - scripts/flow-config-core.py
```
````
> 解析器配套：`allow/deny` 为**标量序列**，故 `flow-core.py` 的受限 YAML 解析器需一处**向后兼容扩展**——`_parse_list` 接受 `- 标量`（现仅 `- key: value`）。这是**纯增量**（只多接受一种形状），`dump_yaml` 已支持序列标量输出，S1 roundtrip 与既有 33 单测不受影响（回归护栏见 §6.3）。

### 4.2 diff 范围核对策略

**目标**：验证执行器改动未超出任务书/方案范围（红线「执行器写权限关进测试门」）。

**输入**：`executor/diff.patch` + `result.json.diff.changed_files(+untracked_files)` + scope 声明。

**scope 解析优先级**：
1. `verify --scope FILE`（显式 allow/deny 清单文件，格式同前置块 `diff_scope`）。
2. taskbook.md ` ```flow ` 前置块 `diff_scope.allow/deny`（glob，支持 `scripts/*.py`）。
3. 无声明 → `diff_match=false` + `scope_undeclared`（**fail-closed**，report-only，需 critic 确认）。

**核对算法**：
1. `changed = changed_files ∪ untracked_files`（过滤 `.flow/`、`.git/`、gitignore 项）。
2. 对每个改动文件：
   - 命中 `deny` → 立即 `out_of_scope`（如碰到 P1 冻结文件 `scripts/dsh-design` 直接 fail，且这是红线违例）。
   - `allow` 存在 → 文件必须匹配 `allow`（fnmatch glob），否则 `out_of_scope`。
   - `allow` 不存在且 `deny` 存在 → 允许（deny-only 模式）。
3. `diff_match = (out_of_scope 集合为空) 且 scope 已声明`；否则 false。

**产物**：`verify.json.details.diff = {changed_files, allow, deny, out_of_scope[], scope_verdict: in_scope|out_of_scope|undeclared, stat}`。`verify.md` 打印逐文件结论。

**边界（自动 vs 人工）**：文件级范围核对**全自动**（确定性）；「改动内容是否语义上符合方案」（文件对了但内容跑偏）仍属 critic 复核，作为 verify.md 提示、不硬卡——避免把语义判断冒充成可自动判定的门。

### 4.3 错误处理表核对（自动 vs 人工边界）

**输入**：`design.md` 的附录风格错误处理表（markdown 表，列 `# | 错误场景 | 处理 | 测试覆盖`）。

**解析与核对**：
1. 定位设计稿中该 markdown 表（以首列匹配 `E\d+` 识别行）。
2. 逐行判 `covered`：`处理` 单元格非空 **且** `测试覆盖` 单元格非空（引用具体用例/文件）。
3. 增强（best-effort）：在 `changed_files` 中的测试文件 grep `E-id`/场景关键词；定位不到标 `grep_miss`（仅提示，不降级）。
4. 汇总：
   - `error_table_match=true` ⇔ 表存在 且 所有行 `covered`。
   - 任一行未覆盖 → `false` + `uncovered: [E1,E3]`。
   - 无表/不可解析 → `false` + `error_table_missing`。

**边界（明确自动 vs 人工）**：

| 维度 | 自动 | 需 critic 人工确认 |
|---|---|---|
| 表是否存在/可解析 | ✅ | — |
| 每行「处理」「测试覆盖」非空（结构覆盖） | ✅ | — |
| 测试文件里能否 grep 到用例引用 | ✅（提示） | — |
| 处理是否**语义正确**、测试是否**真正触发**该错误 | ❌ | ✅（verify.md 列 `human_review[]`，advisory） |

**红线**：结构覆盖是硬门；语义正确性是 critic 职责，写进 verify.md 供 reviewer 复核，**不冒充自动判定**。

### 4.4 `executor/verify.json`（扩展）与 route 推导

```json
{"schema_version":1,"tests_pass":true,"diff_match":true,"error_table_match":true,
 "route":null,"checked_at":"2026-08-14T10:00:00+00:00",
 "details":{
   "tests":{"command":"python3 -m unittest discover tests","exit_code":0,"output_tail":"…"},
   "diff":{"scope_verdict":"in_scope","out_of_scope":[],"changed_files":[…]},
   "error_table":{"total":12,"covered":12,"uncovered":[],"human_review":[]}}}
```

> `tests_pass/diff_match/error_table_match/route` 四键与 P2 §1.6 完全一致，读取方（`read_verify` / `build_ctx` / `test_gate_pass` 守卫）零改动；`details` 为向后兼容的增量字段。

**route 推导（`--auto` 无 `--route` 时）**：

| 失败条件 | 推导 route | 理由 |
|---|---|---|
| `tests_pass=false` | `impl` | 实现未过测试 → 重执行 |
| `diff_match=false`（out_of_scope） | `impl` | 执行器越权写 → 重执行（收紧 scope） |
| `error_table_match=false` | `design` | 方案错误处理表不完整 → 回设计补表 |
| `tests_pass=false`（command_unresolved） | `design` | 任务书缺测试命令声明 → 回设计补声明 |
| `diff_match=false`（scope_undeclared） | `design` | 任务书缺 scope 声明 → 回设计补声明 |

`--route` 可覆盖（人工兜底）；推导结果记入 `details` + verify_fail 事件 meta。

## 8. P4 / P5 衔接

### 8.1 P4（跨设备执行面）

- `ExecutorSpec.runtime.os` 即执行面的**能力声明**：P4 控制面 `flow sync` 前用它做 preflight（执行器仅 linux → 执行面必须 linux），本设计已把该声明落到 spec 与 `load_executor_spec` 校验，P4 直接复用。
- `executor/result.json`、`diff.patch`、`verify.json`、`design-result.json` 全为 `executor/` 下版本化工件 → 是 P4 git 同步的最小传输单位（`events.jsonl` append-only + `status.yaml` 原子写已就绪）。
- `FLOW_PLANE_ID` / 单写者锁：execute/verify 复用 `_do_transition` 的锁，P4 执行面以 `FLOW_PLANE_ID=execution` 取锁，控制面写 design/taskbook、执行面写 executor/verify 天然串行。
- 执行面最小集校验：本设计 execute/verify 只依赖 `git + rx + 测试运行器 + flow`，不含 dsh/OpenClaw/模型 key（design 才需要），与架构 §2.4 一致。

### 8.2 P5（复盘与版本化）

- `design-result.json`（model/usage/duration）+ `result.json`（executor/duration/cost）+ `verify.json.details`（tests/diff/error_table 逐项）直接喂 P5 `retro.jsonl` 的 `stages.design/execute/verify` 字段，无需二次采集。
- 错误表逐行结果 → P5 缺陷分类法映射：`uncovered 行`→`error_handling_missing`、`out_of_scope`→`impl_differs_from_design`、`test_command_unresolved`→`untranslatable`（任务书不可执行=翻译缺陷）。
- `test_command`/`diff_scope` 作为任务书**结构化声明**进入 `process/` 流程版本（semver minor：新增「错误处理表核对门」与「diff 对照门」即一次 minor bump），`process_version` 随 work-item 记录，P5 `process_migrate` 校验旧任务书对新 schema 的可读性。
- `verify.md` 的 `human_review[]` 聚合 → P5 复盘「人工耗时/复核项」口径，驱动「哪些核对可进一步自动化」的升级决策。
