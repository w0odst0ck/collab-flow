# 链路畅通运维方案 v2.0 — 事件驱动链式推进（Chain-on-Transition）

> 2026-08-24 ｜ collab-flow 仓 ｜ 背景：08-24 execute 前置状态三连 fail 复盘
> v1.0 教训：cron 轮询检查是偷懒——检查是因为链条不会自动前进；正确做法是**架构内建推进**，
> 状态一变的当场触发下一步（推模式），不靠定期巡检（拉模式）
> 目标：链路推进是系统内建行为，不是外部巡检职责

---

## 1. 问题本质

```
created →design→ designed →review→ reviewed →translate→ translated →execute→ executed →verify→ verified →accept
```

- 自动段（design/execute 由 pump 拉起）不断；断点全在**状态转移后的下一步没人触发**
- v1.0 的 health cron / auto-advance cron 都是**拉模式**：周期性全量扫描发现问题——
  滞后（扫描间隔内不可见）、依赖 cron 存活、治标不治本
- 根治：**推模式**——每次状态转移发生时，当场执行「转移后动作」，链路自己往前走

## 2. 架构设计：Chain-on-Transition（转移即推进）

### 2.1 核心：post-transition 钩子（flow-core 扩展）

状态机已有 `TRANSITIONS` 表（每步转移 + guard + effects）。扩展为：**转移完成后执行钩子链**。

```yaml
chain:
  enabled: true
  on_designed:   auto_review        # design 完成 → 自动 review（或标记待审）
  on_reviewed:   auto_translate     # review 过 → 当场生成 taskbook
  on_translated: auto_enqueue       # translated → 当场入队 execute（scheduled 到下一空闲窗口）
  on_executed:   auto_verify        # execute 完成 → 当场 verify --auto
  on_verified:   notify_accept      # verified → 即时推送「待 accept」（必须人）
```

- **触发位置**：`_do_transition` 写 status.yaml 的公共路径——无论 transition 是手动命令
  （`flow workitem transition`）还是 pump 内部完成（design/execute 任务终态写状态），
  **全部走同一钩子**。状态一变，下一步当场发生，零延迟、零轮询。
- **同步执行**：钩子在 transition 返回前完成（auto_review 的机械检查是确定性的毫秒级；
  LLM 语义审可异步入队下一窗口——但「入队」这个动作本身当场完成）
- **等窗口不靠轮询**：auto_enqueue 入队时用 window.py 算出下一空闲窗口写 `scheduled_at`，
  pump（本就在跑的调度器）到点自然拉起——调度是 pump 的既有职责，不新增巡检

### 2.2 任务终态钩子（flow-task-core 扩展）

pump runner 的任务终态处理（done/failed/timeout）是**既有代码路径**，在此处追加：

| 任务终态 | 追加动作 |
|---|---|
| design done | 确认 workitem → designed → 触发 on_designed 钩子（review 链） |
| execute done | 触发 on_executed 钩子（verify 链） |
| execute failed/timeout | 即时推送失败报告（不是等巡检发现） |

### 2.3 超时兜底：pump 心跳顺带（非新 cron）

- **不新增任何 cron**。pump 是系统生命线（每分钟调度 scheduled 任务），在其 dispatch 循环
  末尾顺带做卡点超时检查（同一进程同一循环，几乎零成本）
- 超时演进（每卡点按最后事件计时）：<2h 静默 → 2-24h 推送提醒 → >24h 升级提醒 →
  >48h 强制收口（R1 机械+LLM 双检自动 pass / R2 自动生成 / R3 自动入队 / R4-R5 stale 归档）
- 超时检查的数据来自**事件日志**（events.jsonl 已有），不新增状态

### 2.4 提醒：推模式（事件即时推送，替代定期推送）

| 事件 | 即时推送 |
|---|---|
| workitem 卡点出现（>2h 未动） | 飞书提醒（非轮询发现，是超时时刻触发） |
| 超时升级 / 强制收口 | @用户 + 明示动作 |
| execute 失败 | 失败报告（含 failure_tail 指引） |
| verified 待 accept | 「待拍板」推送 |

### 2.5 flow health 降级为诊断工具

- `flow health` 保留为**人主动跑的全局状态查看**（一次查看所有仓卡点），
  不再承担运维巡检职责；flowq 面板照旧（可视化，非巡检）

## 3. 质量保护（不变，且更紧）

- auto_review 的 pass 底线：**机械检查确定性判定**（design.md 完整性/测试策略/错误处理表/验收对照）
  不过 → 自动 reject 打回；LLM 语义建议只作记录（verdict=机械&&LLM 双过）
- `require_human_review: true` 标记的 workitem：跳过自动 review，只推送提醒（超时 → 归档，不自动放行）
- verify/accept 永远人工（收口型兜底：超时 stale 归档，归档不删除可恢复）
- 所有自动动作写 `events/audit.jsonl`；`--dry-run` 全局开关

## 4. 配置（config/defaults.yaml 扩展）

```yaml
chain:
  enabled: true          # 总开关（false = 完全退化为 v0 半自动 + 提醒）
  on_designed: auto_review      # off|auto_review（默认 off：只推送提醒）
  on_reviewed: auto_translate   # bool
  on_translated: auto_enqueue   # bool
  on_executed: auto_verify      # bool
  warn_hours: 24        # 升级提醒阈值
  force_hours: 48       # 强制收口阈值
  scan_projects: null   # null = 自动 glob ~/.openclaw/workspace/projects/*/.flow
  notify: null          # 推送命令模板（复用 host.notify 模式）
```

## 5. 测试与验收（~50 用例）

- **post-transition 钩子**（~20）：每个转移触发对应钩子（手动 transition 与 pump 内部完成
  两条路径都覆盖）、钩子动作（review/translate/enqueue/verify/notify）、enqueue 的窗口计算、
  dry-run 零写入、require_human_review 跳过、audit 落盘
- **任务终态钩子**（~8）：design/execute done/failed/timeout 的追加动作
- **超时收口**（~10）：超时演进（静默→提醒→升级→收口）、>48h 强制动作、归档可恢复
- **回归**：141 单测全绿 + ruff 干净 + 真实队列冒烟（现有任务不误触发）
- **架构验证**：`transition` 命令返回前钩子已完成（同步语义测试）——证明无轮询依赖

## 8. 细节优化（v2.1 追加，实现时全部纳入）

1. **钩子幂等 + 防重入锁**：同一 workitem 的钩子执行期间加锁（复用 flock），重复触发不产生重复动作
   （如 auto_enqueue 重复入队）；钩子内若有 transition 不递归触发同钩子
2. **钩子失败不阻塞转移**：转移已发生即成功；钩子失败 → audit + 推送，入队失败降级为提醒（不静默）
3. **自动 verify 失败闭环（重试环）**：verify --auto 失败打回 → 自动重新入队 execute（下一空闲窗口）
   + 推送失败原因（测试/越界/错误表三项分别报告），人可干预
4. **风暴防护**：连续失败 N 次（默认 3，可配）→ 冻结 workitem（frozen 标记，停自动推进，升级人工）——
   防自动链死循环（design→reject→重design→…）；FLOW_ITERATION_LIMIT 既有机制对齐
5. **expected_seconds 自适应**：auto_enqueue 时从同仓同类任务历史实际时长（registry）学习估值，
   超时 kill 更准（替代固定 1500s）
6. **并发安全**：钩子执行复用 registry flock，防双进程同时推进同一 workitem（跨仓扫描场景）
7. **scan_projects 排除规则**：默认 glob 自动跳过 `archive/`、嵌套仓（如 work-pool/repo）、
   无 .flow 的目录；可配额外排除
8. **入链感知**：新 workitem 创建时推一条「已入链」（链条开始走的可观测性），卡点出现（>2h）再推提醒
9. **verified 推送带验收摘要**：verify --auto 结果（测试数/越界/错误表）直接进推送，用户一看可判 accept，
   减少往返
10. **graceful degradation**：老 workitem（无 audit/events 产物）钩子兼容跳过；chain.enabled=false
    完全退回半自动 + 提醒，既有流程零影响
